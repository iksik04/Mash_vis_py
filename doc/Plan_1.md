# Блок 1 — Технологический стек и платформа (утверждено)

## 1.1 GUI-фреймворк — PySide6 (Qt for Python)

**Решение:** PySide6 + Qt Designer.

| Аспект | Решение |
|---|---|
| Фреймворк | **PySide6** (LGPL, можно закрывать код) |
| Моделирование UI | **Qt Designer** — визуальный редактор с перетаскиванием виджетов, `.ui`-файлы |
| Интерактивный ROI-редактор | **QGraphicsView / QGraphicsScene** — зум колесом, пан, кастомные QGraphicsItem для углов/сторон/поворота. Логика из `roi_selector.py` переносится почти 1:1 |
| Фоновые задачи (камера, ORB, Tesseract) | **QThread / QThreadPool** + сигналы/слоты — вынос из UI-потока |
| Live-preview с камеры | **QTimer** |
| Таблица результатов валидации | **QTableView + QAbstractTableModel** |
| Настройки приложения | **QSettings** (или конфиг-файл) |
| Интеграция с OpenCV/numpy | Прямая: `np.ndarray` → `QImage` → `QPixmap` (хелпер ~10 строк), без `cv2.imshow` |
| Упаковка | **PyInstaller** (есть хуки для PySide6) |

**Отклонённые варианты:**
- **Flutter + Python** — интеграция только через FFI (C-API) или локальный HTTP/WebSocket; лишний слой, дублирование моделей, IPC-латентность на кадрах 1920×1080, отладка двух процессов. Кроссплатформенность не нужна (Windows-only).
- **Веб-интерфейс** (FastAPI+React, Streamlit/Gradio, Electron/Tauri) — не нужен, т.к. нет требования удалённого доступа / мультиоператора. Точный drag-and-drop ROI поверх изображения в Streamlit/Gradio практически невозможен.

## 1.2 Веб-интерфейс — не требуется

**Решение:** веб-интерфейс не используется.

**Обоснование:** удалённый доступ и многопользовательская работа не требуются. Нативный Qt выигрывает: один язык, один процесс, прямая работа с `np.ndarray`, нет сети, проще `.exe`.

## 1.3 ОС, язык, упаковка

| Параметр | Решение |
|---|---|
| ОС | **Windows-only** (некроссплатформенное приложение) |
| Язык | **Python** (переиспользуем существующий бэкенд) |
| Упаковка | **PyInstaller** → `.exe` |
| Режим распространения | **Portable** — данные рядом с `.exe` (можно на флешке), без инсталлятора и `%APPDATA%` |
| Tesseract | **Бандлить** в дистрибутив (`tesseract.exe` + `tessdata/` рядом), путь вычислять относительно `sys._MEIPASS` / `sys.executable` |

**Следствия для бэкенда (правки, отмечены для блока правок):**

1. **Tesseract:** убрать жёсткий путь `C:\Users\pkirill\AppData\Local\Tesseract-OCR\tesseract.exe` из `ocr.py`; вынести в конфиг + автоопределение (бандл → PATH → реестр → настраиваемый путь).
2. **Пути к данным:** в `constants.py` разделить:
   - **read-only ресурсы** (иконки, дефолтные пресеты) — из бандла (`sys._MEIPASS`);
   - **пользовательские данные** (пресеты, история, логи, учётные данные) — рядом с `.exe` (portable-режим), не в `_MEIPASS` (временная распаковка удаляется при выходе).
3. **Камера:** предусмотреть выбор бэкенда OpenCV (`cv2.CAP_DSHOW` для Windows) — отмечено для блока правок.
4. **Антивирус:** PyInstaller-сборки иногда ложно детектятся; при необходимости — Nuitka (отмечено для блока упаковки).
5. **Размер:** PySide6 + OpenCV + numpy + pytesseract + бандл Tesseract ≈ 150–250 МБ `.exe`; рассмотреть `--onedir` вместо `--onefile` (быстрее старт, проще обновление) — отмечено для блока упаковки.

# Блок 2 — Режимы работы и навигация (утверждено)

## Вопрос 4. Переключение режимов — вариант (б): два отдельных окна

**Решение:** два отдельных окна (`QMainWindow`):
- **Окно «Валидация»** — доступно обеим ролям (оператор и админ).
- **Окно «Настройка»** — доступно только админу (после ввода пароля).

**Поведение по ролям:**
| Роль | Окно «Валидация» | Окно «Настройка» |
|---|---|---|
| Оператор | ✅ видит | ❌ не видит |
| Админ | ✅ видит | ✅ видит |

**Открытие:** стартовый экран/диалог входа (роль определяется по учётным данным из SQLite — см. Блок 1, В2). После входа открывается окно «Валидация»; у админа дополнительно доступна кнопка/меню «Настройка», открывающая второе окно. Оба окна могут быть открыты одновременно (админ может переключаться).

**Открытый вопрос (уточнить в блоке UI-навигации):** стартовый экран — это отдельный диалог логина, или окно «Валидация» сразу с формой логина/кнопкой «Войти как админ»? Рекомендую отдельный диалог логина перед главным окном.

## Вопрос 5. Настройка — вариант (б): свободный редактор

**Решение:** свободный редактор (не визард). Один экран настройки с панелями/вкладками; в любой момент можно переснять реф, добавить/удалить/отредактировать ROI, поменять пороги, сохранить всё разом.

**Типы проверок для ROI — расширяемая модель с чекбоксами:**

Для каждого ROI в момент его выбора в реф-контексте указывается, **что в нём проверять**. Реализуется как **список с галочками** (чекбоксы). Заложена расширяемость: помимо «контур» и «символы» можно добавлять другие типы проверок без переделки модели данных.

**Текущие типы проверок (MVP):**
- ☐ **Контур** (`main_contour` + `cont_bin_threshold` + `min_ext_cont_len`)
- ☐ **Символы (OCR)** (`OCR_allowlist` + `ocr_bin_threshold`)

**Задел на будущее:** модель `checks` у ROI — список/словарь типов проверок с параметрами; в UI — динамический список чекбоксов, подгружаемый из реестра типов проверок. Новый тип проверки = новый модуль + запись в реестре, без правки `SingleROI` и JSON-схемы (параметры хранятся в обобщённом поле).

**Настройка по типам:** после выбора ROI можно **пройтись по всем ROI одного типа** для настройки (например, все ROI с «Контур» — подряд настроить пороги контуров; все с «Символы» — подряд настроить OCR). Это сочетает свободный редактор с удобством пакетного прохода по однотипным ROI.

**Следствия для бэкенда (правки, отмечены):**
1. `SingleROI` — заменить плоские поля `OCR_allowlist` / `main_contour` / `ocr_bin_threshold` / `cont_bin_threshold` / `min_ext_cont_len` на обобщённую структуру `checks` (список/словарь типов проверок с параметрами). Обратная совместимость с текущим JSON v2 — через миграцию (см. Блок 5).
2. `validation.validate` — вместо жёсткой последовательности «контуры → символы» итерировать по включённым у ROI типам проверок.
3. `json_process` — новая схема сериализации `checks` (версия JSON — см. Блок 5).

## Вопрос 6. Пресеты — вариант (б): менеджер пресетов + сценарии валидации

**Решение:** менеджер пресетов (создать/копировать/переименовать/удалить/выбрать). Каждый пресет — папка с `Ref_img_context.json` + `MultiROI_context.json` + картинками (структура `presets/<preset_name>/...`).

**Метаданные пресета — в SQLite** (таблица `presets`: имя, описание, дата создания, автор и т.п.). JSON остаётся «рабочим» форматом конфигурации; список/метаданные/связи — в БД.

**Импорт пресета — нужен** (архив `.zip` для переноса на другой ПК). Экспорт — очевидно, тоже нужен (симметрично).

**Сценарии валидации (новое понятие):**
- **Сценарий** — именованный набор «пресет + параметры запуска», который оператор выбирает перед валидацией.
- У каждого сценария — **отдельно указанный пресет**.
- **Настройку сценариев и выбор пресета выполняет админ** (в окне «Настройка»).
- **Оператор** нажимает две кнопки: **«нужный сценарий»** (выбор из списка) → **«Пуск»**.

**Модель данных (SQLite, черновик — уточним в Блоке 5):**
presets (id, name, description, created_at, author_id, folder_path)
scenarios (id, name, preset_id, description, created_at, created_by)
-- позже: parameters (пороги и т.п.), если сценарий их переопределяет

**Уточнения, зафиксированные:**
- Активный пресет **не глобальный** — он выбирается **через сценарий** перед валидацией.
- Несколько сценариев валидации — да, каждый со своим пресетом.
- Настройка сценариев — только админ.
- Оператор: выбор сценария + «Пуск» (минимум действий).

**Открытый вопрос:** может ли один пресет использоваться в нескольких сценариях? (Рекомендую да — связь `scenarios.preset_id` many-to-one.) Может ли сценарий переопределять параметры пресета (например, пороги валидации)? Рекомендую заложить поле `parameters` (JSON) в `scenarios` на будущее, в MVP — пусто.

# Блок 3 — Экран «Настройка» (утверждено)

## Вопрос 8. Структура экрана «Настройка»

**Решение:** компоновка из трёх зон (левая панель / центр-изображение / правая-свойства), **расположение меняется по ходу разработки** (использовать `QDockWidget`, чтобы панели можно было перетаскивать/скрывать; финальную компоновку зафиксируем позже).

**8.1 Компоновка:** три зоны на `QDockWidget`:
- **Левая панель:** источник кадра (камера ▾, разрешение ▾, «Снимок», «Из файла…»), реф-контекст (порог бинаризации + слайдер), список ROI (`+ Добавить`, список с чекбоксами/иконками статуса, `Удалить`, `Дублировать`, `Пакетный проход…`).
- **Центр:** `QGraphicsView` — кадр, внешний контур, рамки ROI, интерактивное редактирование выбранного ROI.
- **Правая панель:** свойства выбранного ROI (имя, позиция/размер/угол — числовые поля, чекбоксы типов проверок, параметры «Контур» и «Символы», live-превью распознанного текста, `Применить`/`Сбросить`).
- **Статус-бар:** пресет, dirty state, подсказки.

**8.2 Меню «Пресет» — только выпадающее** (без отдельного диалога «Менеджер пресетов»): Новый, Открыть, Сохранить, Сохранить как, Импорт `.zip`, Экспорт `.zip`, Удалить.

**8.3 Меню «Сценарии» — диалог из настроек** (открывается из меню «Настройка», не отдельное окно).

**8.4 Параметры валидации (пороги `EXT_COUNTUR_MATCH_THRESHOLD`, `ROI_CONTOUR_MATCH_THRESHOLD`) — отдельный экран в меню «Сценарии»** (не в окне «Настройка»).

## Вопрос 12. Режим запуска — вариант (в): оба режима

**Решение:** переключатель Single / Continuous (live). По умолчанию — **live**.

| Аспект | Решение |
|---|---|
| 12.1 NG в live | **обозначать красным, как сейчас** (подсветка статуса, без остановки потока) |
| 12.2 Частота live | **каждый кадр**; если обработка занята — **пропуск кадра** (обрабатываем следующий доступный) |
| 12.3 Автозапуск | **без автозапуска** — только по кнопке «Пуск» |

**Запуск:** оператор выбирает сценарий в выпадающем списке → «Пуск». «Стоп» останавливает live-поток.

**Следствия для бэкенда (правки):**
- Live-цикл в `QThread`: захват кадра → если поток обработки свободен, `validate` → сигнал в UI → обновление; иначе кадр пропускается.
- `validation.validate` вызывается покадрово; результат — через сигналы Qt (слоты в UI-потоке).

**15.3 `TesseractNotFoundError`** — **«продолжить без OCR»** (SKIP всех OCR-проверок) / «выход».
